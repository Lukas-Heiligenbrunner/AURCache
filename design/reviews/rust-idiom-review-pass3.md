# Rust idiom review — pass 3

Read-through of the whole backend workspace (all crates, file by file) for
non-idiomatic code and simplifications. Pass 1 (`rust-idiom-review.md`) was
driven by clippy; pass 2 (`rust-idiom-review-pass2.md`) was a read pass with
reasonably confident fixes applied inline. This pass is the second read pass.

Those structural items too large or risky to apply inline landed here, plus the
list of what was applied directly, so nothing floats.

## Larger / structural recommendations

### `aurcache-api/src/build.rs` — `get_build` duplicates `build_by_number`

*Applied — see "Second batch" above.*

### `aurcache-api/src/aur.rs` — search returns untyped errors

The search path reports one of several failure classes (RPC timeout/HTTP vs. a
malformed response) but maps everything to a single error message. Consider
differentiating timeout vs malformed, or at least keeping the underlying
`reqwest` error in the message. (Also note: the route still carries per-request
AUR round trips while `/api/package/<pkgbase>` was made column-backed — worth
reviewing whether search need the same treatment.)

### `aurcache-api/src/package.rs` — `get_package` handler

*Partially applied.* The inline latest-build query and the source/version match
are now helpers (see "Second batch": `latest_successful_version_any_platform`,
`package_source_and_version`). A `PackageDetail::from(row, …)` builder alongside
the typed summary structs is not worth the churn — the remaining handler is
mostly field copying into `ExtendedPackage`.

### `aurcache-api/src/worker.rs:525` — `complete_job`

The largest single handler in the API. It mixes HTTP concerns (auth, JSON body,
job descriptor validation) with the bulk of the worker protocol state machine.
The parts that just pass through to `aurcache_utils::worker_complete` are thin;
the parts that do their own DB/state work (lease check, upload validation,
`approval` tri-state handling) would belong in `aurcache-utils` or a dedicated
`aurcache-worker-protocol` module so the route is a thin adapter. Also several
`#[post]` routes here share a `watch_pkgbase`-style preflight; consider a
`FromRequest` guard.

### `aurcache-scheduler/src/update_version_check.rs` — `check_versions` Aur/Git arms

*The RPC part is already resolved:* `check_versions` calls
`client.multi_info_of(&names)` (aurcache-deps), which is the chunked
`rpc_info_all` helper, so no local RPC loop exists. The remaining duplication —
the Aur and Git arms each do refresh + `sourceinfo_and_metadata` +
`apply_source_metadata` + `sync_vcs_sources` + `upstream_is_newer` +
`out_of_date` — could collapse into a shared
`resolve_latest_version(source, store)` helper, but the arms differ where it
matters (upstream version source, `aur_missing` handling) and the in-arm
comments carry the why. Left as-is.

### `aurcache-cli/src/main.rs:1184-1318` — build states re-encoded as bare `i32`

*Applied — see "Second batch": `BuildStates::*` comparisons and a
`BuildState::from_i32`-based `build_status_label`.*

### `aurcache-utils/src/repo_ingest.rs` — parallel vectors

*Applied — the `build_pkgs` tuple and `file_infos` became one `IngestPkg`
struct; "parse and stage" stays in `ingest_pkgs_in` where the lease ordering
makes it hard to split further.*

### "Latest successful build for a dependee" duplicated

*Applied — see "Second batch": `aurcache-db/src/helpers/builds.rs`
`latest_successful_version(db, pkg_id, platform)` is now used by both
`worker_complete::dependency_satisfied` and `update.rs::dependency_satisfies_constraint`
(whose StartTime tie-break had silently diverged). The migration note below
stands only as history.

### `aurcache-worker` & `aurcache-worker-docker` — successor-size functions

- `aurcache-worker/src/job.rs` `run_job` (line 34) / `run_job_inner` (67) /
  `run_build` (270): three layers that each do chroot setup, credential
  staging, config writing, and output streaming with only slightly different
  ordering. Hard to read top-down.
- `aurcache-worker-docker/src/executor.rs` `run_job` (349): same shape with
  docker-specific concerns.

Consider extracting the shared job harness (step sequence + failure handling)
into `aurcache-worker-core` with parameterized "how to create the build
sandbox", so `aurcache-worker` (devtools chroot) and `aurcache-worker-docker`
(container) become thin differences instead of near-duplicate 300-line flows.

### `aurcache-worker-core/src/report.rs` — exit classification

*Applied — see "Second batch": the cancel shape is now one `canceled_report`
shared by `classify_exit` and `classify_exit_canceled`. The per-entry-point
selection remains because the two constructors genuinely differ (cancel observed
during setup has no exit status).*

### `aurcache-worker/src/credentials.rs` — `StagedCredential.key` is write-only

*Applied — the field is gone; staging is still asserted via the fixed `KEY_FILE`
path, and the struct doc no longer overpromises about `augment_makepkg_conf`.*

### `aurcache-worker/src/job.rs` — helpers nearby

`pump_output` (line ~225) batching constants/logic is duplicated between
`run_build` and the log stream — and `aurcache-worker-docker` has its own copy
in `executor.rs` (`stream`/`log` batching). A shared `log_stream`/`pump_output`
in `aurcache-worker-core` would keep the two workers' upload throttling
identical. Same story for `append_block`/`spawn_devtools` and the fingerprint
normalization shared with the enroll flow.

### `pacman-mirrors/src/status.rs` — `get_from_url` takes an unused `Platform`

*Applied — the dead platform plumbing through `fetch_status`/`get_from_url` was
dropped (both URLs serve x86_64; the aarch64/armv7h cases bail in
`get_from_default_url`, so the param could never receive another value).

### `pacman-mirrors/src/benchmark.rs` — `Bench` trait has a single impl

The `Bench` trait with `async fn time("…")` exists to make one concrete type
(`Benchmarker`) injectable. With a single implementation and no tests driving
multiple impls, an `impl`-returning enum or a bare `async fn` (RPITIT where a
trait is actually needed) would cut the indirection. Also `gen_mirrorlist`
re-parses/serializes URLs it already has in memory.

### `pacman-repo-utils` — package-add pipeline is O(repo) per add

`repo_add` re-archives the entire `.db`/`.files` each `add`: every add rewrites
the whole tar.gz, turning N adds into O(N²) I/O. The `desc`-into-files write at
`repo_add.rs:95` is *correct*, not a copy-paste — the alpm-repo-db spec's
"default with files" variant requires a `desc` and a `files` file per package
directory in `repo.files` (the `desc` "is the same as in the default database").
Also `calc_checksums` reads whole files into memory — stream the digest instead.

### `pacman-repo-utils/src/repo_database/db.rs` — rewrite scaffold duplicated

*Applied — see "Second batch": `rewrite_archive(db_archive, keep, fill)`.*

### Migrations — duplication is by convention

`aurcache-db/src/migrations/*` modules repeat the Postgres/SQLite `execute`
pairs (m20260818, m20260826, etc.). This is deliberate (no migration framework
here), so keep as-is; keep migrations sequential and per-change rather than
merging.

### `aurcache-db/src/helpers/worker_jobs.rs` — duplicated query shapes

`waiting_reasons`, heartbeat, and the queue-status queries each restate
"filter by build status (list) then group". A query-builder helper
(e.g. `builds_in_states(states, platform)` → `Select`) would cut ~30 lines of
near-identical sea-orm chains. The heartbeat `contains` → `HashSet` idea was
reviewed and **rejected** here: the vectors are small (`MAX_JOBS = 4`), and the
churn buys nothing.

### `aurcache-db` migrations — `ActiveValueExt::get` reuse

The migration helpers re-read columns off `ActiveModel` with `.get` where the
new `ActiveValueExt` in `helpers/active_value_ext.rs` would be the single path.
Low value — the migrations are frozen once merged; only new migrations benefit.

### `aurcache-db` fixtures — `dependency_backfill.rs` dedupe

The backfill migration's fixtures (two packages, one AUR dep) repeat the row
setup of several `aurcache-utils` tests. Fine to leave; fixtures are test-local
by design, but if backfill grows a third scenario, factor the base-package
insert helper.

### `aurcache-activitylog` — `Display` vs `format!`

*Resolved — investigated, nothing to change.* `ActivitySerializer::format()` has a
single call site (`ActivityLog::list`), the activity structs are passed to
`ActivityLog::add` whole (serialized as JSON for the `data` column), and no call
site debug-formats an activity; the earlier "conflicting `{e:?}` formats" note
was a misread.

### `dir_size` — duplicated across crates

*Applied for the worker copy.* `aurcache-worker/src/cache.rs` had its own
best-effort recursive `dir_size`; it now uses
`aurcache_utils::utils::dir_size::dir_size(...).unwrap_or(0)` (aurcache-utils was
promoted from a dev-dependency to a regular one — it is already compiled into the
worker's test graph). The only other use is `aurcache-api/src/stats.rs`, already
on the shared fn. Note the shared fn propagates a nested read error where the old
worker copy skipped just that subtree; both are only invoked on worker-owned
directory trees.

### Repo path constants (`./repo`, `repo/{platform}`)

The repo root is re-derived in several places (`aurcache-deps`
`default_repo_root()`, `aurcache` startup's `init_repo`, the ingest default in
`aurcache-utils`, `stats.rs`, the `m20260508_…` data migration). There is *no*
`REPO_ROOT` env var (the compose files mount `/app/repo` and the server runs from
`/app`, so the hardcoded `./repo` is correct as-is). A single shared `repo_root()`
fn would keep the layout in one place; the migration's `./repo` is a baked-in data
migration and should keep its own literal. Not applied — it would touch every
crate's test setup for marginal gain; noted here for a future layout change.

## Considered and rejected

- Replacing the `sleep_until_next_fire`/cron machinery with `tokio-cron` or
  similar — existing `cron` crate works, tiny surface, not worth a dep change.
- Turning the `STATUS_*` constants into a SeaORM enum type — `BuildStates` is
  i32-by-wire; the ints are semantically stable and used in raw SQL
  (`stats.rs`). Keep.
- Applying `#[expect]` vs workspace-lint changes — keep the existing policy:
  lints stay enabled in `backend/Cargo.toml`; suppress locally where a lint
  does not fit.
