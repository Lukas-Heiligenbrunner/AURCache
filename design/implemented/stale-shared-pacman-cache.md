# Rebuilding a package at the same version poisons the shared pacman cache

How the worker recovers when a package is removed from AURCache and re-added at
the same version, so the rebuilt artifact has different bytes from the one that
was cached.

Status: **implemented** — worker-side reconcile + promote-time validation
against the served `repo.db`, no server or protocol changes.

---

## The failure

`libdbusmenu-gtk2` was deleted from AURCache and re-added at the same version,
so its rebuilt artifact (`libdbusmenu-gtk2-16.04.0.r498-3-x86_64.pkg.tar.zst`)
had slightly different bytes and a different checksum from before. On TrueNAS a
later build needing it as a dependency failed:

```
:: File /var/cache/aurcache-worker/pacman-pkg/libdbusmenu-gtk2-16.04.0.r498-3-x86_64.pkg.tar.zst is corrupted (invalid or corrupted package (checksum)).
error: failed to commit transaction (invalid or corrupted package)
Do you want to delete it? [Y/n]
...
==> ERROR: 'pacman' failed to install missing dependencies.
```

Reproduced on the same worker against `steam-native-runtime` (which depends on
`libdbusmenu-gtk2`), confirming root cause end to end.

## Why

The worker's shared pacman cache (`<cache>/pacman-pkg`) is bind-mounted
**read-only** into every chroot as the second `CacheDir` (`chroot.rs`'s
`with_cache_dirs`; `arch-nspawn` mounts the first `CacheDir` read-write, the
rest read-only). Writable downloads go to each job's private cache.

When a cached file's bytes no longer match the current `repo.db`, pacman skips
re-downloading (the file exists in some cache), fails integrity at install,
offers to delete it — and cannot, because the mount is read-only. The whole
dependency install aborts.

## Why it stays broken

The cache is deliberately read-only so a build cannot corrupt shared state. The
only authoritative statement of what a package *should* look like is the
server's `repo.db`, generated by `repo-add`, on the mirror the workers already
read. A file can only go stale two ways, both inside the worker:

- **(a)** the `repo.db` entry for a filename changes — the delete-and-re-add
  incident — while the old bytes sit in the shared cache;
- **(b)** a promote lands deviant bytes (e.g. a job fetched the *old* artifact
  of a dependency that was rebuilt mid-build).

## Design

Reconcile the shared pacman cache against the aurcache `repo.db` from the
worker itself, **outside** the chroot, where the cache is writable. Official
repository (core/extra/multilib) packages never appear in the aurcache
`repo.db`, so they are untouched — only AURCache's own packages are considered
"mutable", which is exactly where same-version rebuilds can happen.

### The database, fetched conditionally

The DB URL is derived from the already-rendered `[repo]` section
(`repo_db_url` in `aurcache-worker-core`) rather than guessed: the filename is
`<section-name>.db` (a section renamed elsewhere keeps working), `$arch` is
substituted, and the `Server =` line must parse as an `http(s)` URL with a host
and no query/fragment. A violation yields no URL, and no reconcile.

The worker fetches `repo.db` **per job** — once before the chroot is prepared,
and again (conditionally) at promote — because it changes on every build: each
completed build appends a package. Freshness comes from `If-None-Match` /
`If-Modified-Since` (`aurcache-worker/src/repo_db.rs`, via a
`get_conditional` on `WorkerClient`), with the bytes *and the already-parsed
map* cached per URL; a `304` replays the parse for free.

**A failure never returns a stale copy.** A network error, a non-200/304
status, or an unparseable body is an `Err` carrying the URL; the caller emits a
prominent structured `tracing::warn!` and skips the reconcile (or skips
validation at promote). Reconciling against yesterday's DB is exactly how a
fresh stale file sneaks back in.

### The reconcile, event-driven

(`reconcile_pkgs` in `aurcache-worker/src/cache.rs`.) An in-memory manifest
maps `(cache dir, filename) → the repo.db sha256 we last verified`. An entry
records a single-writer fact: the shared cache is written only by this worker
(chroots mount it read-only), so a cached AURCache file can only go stale when
its `repo.db` entry changes — which the manifest catches by *comparison*, with
no stat and no hashing for an unchanged file.

For each `repo.db` entry:

- manifest has the same sha → nothing to do;
- file absent → record the sha (nothing to verify until a promote lands it);
- size ≠ `%CSIZE%` → unlink the archive and its `.sig`, drop the record;
- size matches → hash the file; keep it and record the sha, or unlink + drop.

Hashing is the only real cost and it is batched: serial while the suspicion is
small, and past a threshold (8 files) split across
`min(suspects, available_parallelism())` `std::thread::scope` workers — the
one case that matters is a restart's first pass, which re-verifies the whole
repository at most once. Files the DB does not name are left alone entirely:
absence from the aurcache repo is not staleness.

### The promote, validated

(`promote_job_pkgs(label, repo_db)`.) Every job artifact the (freshly
re-fetched) DB names is size-checked then hash-checked **before** it enters
the shared cache, so case (b) cannot land. A mismatch is refused — "the
repository no longer publishes these bytes" — and stays in the job's writable
cache (which is then wiped; the artifact is garbage at this point). This is not
a formality: the whole point of the change is that a build can start while the
repository still carries the *old* bytes of a same-version rebuild, download
them, and finish after the new ones are live.

Accepted files are recorded in the manifest (the DB just vouched for them, so
the next reconcile costs nothing). When the DB could *not* be fetched, promote
still happens — artifacts are never silently dropped — but the promoted names
are recorded as *unverified*, and the next reconcile hashes them from scratch.
That is the value of the per-file manifest: an unvalidated promote cannot
re-establish trust in stale bytes.

### Two sources of staleness, one loop

(a) is removed by the reconcile the moment the rebuilder publishes its new
bytes and the next job starts; (b) is prevented by the promote check, and if
that check was skipped (fetch failed) the manifest clearing drags the
offender into the next reconcile's hash path. Either way the read-only cache
is clean again before a chroot reads it, and the steady state is one cheap
`304` and a few hash-map lookups per build.

## Recorded decisions

- **No global "DB unchanged" gate.** `repo.db` changes on *every* build — each
  completed build appends a package — so a gate on the whole file would trip
  every job and skip the reconcile constantly. The per-file manifest keys off
  *that file's* entry, which only changes when that file is rebuilt.
- **Per-file manifest, in memory, not TTL.** A time-based eviction would force
  re-hashing on a timer; the manifest re-verifies only what changed, and a
  worker restart costs at most one verify-everything pass.
- **Conditional HTTP, not TTL, for the DB.** Same cheapness argument; `304`
  plus a cached parse has no clock to get wrong.
- **Size prefilter before hashing.** `%CSIZE%` is in the DB next to
  `%SHA256SUM%`; `repo-add` writes both, so a size mismatch skips the hash
  entirely.
- **Absence from the DB is not staleness.** Official packages share this cache
  and are not in the aurcache DB.
- **Residual caveat: no repo provenance in the cache.** If an official package
  and an AURCache one ever share a filename with different bytes, the reconcile
  could churn (delete, refetch, delete). A separate cache namespace is the
  documented future work; it is deliberately out of scope here.
- **Failure is a warning, not a blocker.** The build proceeds without a
  reconcile; refusing to build would turn a mirror hiccup into a worker outage.

## Implementation map

- `backend/aurcache-worker-core/src/repo.rs` — `repo_db_url(section, arch)`
  (requires `url = "2"` in `aurcache-worker-core/Cargo.toml`).
- `backend/aurcache-worker-core/src/client.rs` — `WorkerClient::get_conditional`
  (304 → `None` body, 200 → bytes plus validators).
- `backend/aurcache-worker/src/repo_db.rs` (new) — per-URL
  `{etag, last_modified, bytes, parsed map}`, 304 replay, errors never stale.
- `backend/aurcache-worker/src/cache.rs` — `parse_repo_db`, `sha256_file`,
  the `VERIFIED` manifest, `reconcile_pkgs`, validated `promote_job_pkgs`,
  `hash_suspects` (gated `std::thread::scope`).
- `backend/aurcache-worker/src/job.rs` — fetch + awaited
  `spawn_blocking(reconcile_pkgs)` after source download and before chroot
  prep; fresh conditional re-fetch at the promote step, passed as
  `Option<&RepoDb>`.

No new dependencies outside `aurcache-worker-core`; `flate2`, `tar`, `sha2`
and `hex` were already worker deps.

## Verification notes

The tests cover: URL derivation and its rejection cases; parsing a real
gzip-tar DB; size-mismatch removal without hashing; same-size/hash-mismatch
removal; matching files left alone (and no-op re-runs); official files left
alone; promote refusing stale bytes (both size and hash paths); a validated
promote seeding the manifest; and an unvalidated promote being re-checked and
removed by the next reconcile. The TrueNAS failure was reproduced before the
change; with the worker binary rebuilt from this code, the same rediscovered
cache entry is removed at the start of the job that needs it.
