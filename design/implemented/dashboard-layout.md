# Design: Dashboard layout

Status: **Implemented** · Last updated: 2026-09-22

## Goal
Give the dashboard a glanceable, action-oriented layout that answers "is the instance healthy and what happened lately?" without leaving the page, while keeping the existing `StatTiles` and `Builds per month` chart that already work.

## Success Criteria
- A user landing on `/` sees headline health (tiles) and trend (chart) in the first viewport, and within two: what changed lately (recent packages, recent builds, recent problems) plus attention-needed slices (failed, out of date needing a hand, stuck queue, largest, longest) with links. On a healthy instance the attention cards collapse to one line each, so the page is shorter, not emptier.
- The dashboard is one request per tick (`GET /stats/dashboard`) beside the existing `stats`/`graph`, not one per card. A section the server could not read comes back `None` and renders an inline `alert-error` in its own card; the others render normally.
- Text, grid lines and chart follow the `daisyUI` theme (`oklch(var(--bc))` etc.) on `light`/`dark`/`system` and remain readable on `2560px` and `375px` widths.
- Every slice is ordered, filtered and capped in SQL (`LIMIT 5`), not by fetching whole lists to sort five rows client-side, and the builds slices are served by indexes.
- All existing dashboard SSR tests continue to pass; new sections have `dioxus_ssr` unit tests and a browser smoke for links.

## Context And Current Facts
- **Current landing page** `frontend-rs/src/screens/dashboard.rs:10-78` (`Dashboard`): fetches two resources - `client.stats()` (`aurcache_common::api::stats::ListStats` `stats.rs:6-33`: `total_builds`, `successful/failed`, `recent_*` (7-day `RECENT_DAYS:7`), `avg_build_time`, `repo_size`, `requested/dependency_packages`, trends) rendered as `StatTiles` `dashboard.rs:100-165` (5 cards in `grid gap-4 grid-cols-2 lg:grid-cols-3 xl:grid-cols-5`, two linked), and `client.graph()` (`GraphDataPoint` `stats.rs:43-52`: `year/month/count/successful`) rendered as `BuildsChart` `dashboard.rs:172-238` (`LineChart` 900x260, `padding 20/50/30/45`, two series `started` vs `succeeded`, legend, `chart-box h-64` fix in `index.html:28`).
- **Polling:** `poll::use_poll(stats, false)` / `graph` - slow tick, not busy. Cards already use `bg-base-100 shadow-xl` and `Chart` uses `oklch(var(--bc))` CSS overrides added for `dx-grid-label`/`dx-grid-line` plus `translateY(6px)` for hanging month labels, all in `index.html`.
- **Read APIs today** `backend/aurcache-client/src/lib.rs`: `list_packages(limit, page, dependencies: bool) -> Vec<SimplePackage>` (`/packages/list`), `list_builds(pkgbase: Option<&str>, limit, page) -> Vec<Build>` (`/builds` or `/package/{pkgbase}/builds`), `log(limit, offset, &LogQuery)` -> `LogPage` (`/log` - paged and filtered server-side by `severity`/`since_boot`/`kind`/`entity`, `total` travels with the page; each `LogEntry` decodes to an `Event` whose `sentence()` names its entities), and `stats`/`graph` served from `aurcache-api/src/stats.rs` (`#[get("/stats")]`, `#[get("/graph")]`). `SimplePackage` (`aurcache-common/src/api/package.rs:97`) carries `name`, `directly_requested`, `status: i32`, `outofdate: i32`, `latest_version`, `upstream_version`, `total_size: Option<i64>`; `Build` (`BuildSummary`, `api/builds.rs:7`) carries `number`, `pkg_name`, `version`, `status`, `start_time`, `end_time`, `platform`, `size`, `peak_memory`, `worker_name`, and `waiting_reason` (`Affinity`/`Arch`/`Offline`, attached by `annotate_waiting` in `aurcache-api/src/build.rs` for an `ENQUEUED` build no approved worker can take).
- **What `start_time` means:** it is set to the enqueue time (`enqueue_build_if_missing`, `aurcache-utils/src/package/update.rs`) and overwritten with the claim time when a worker takes the build (`aurcache-db/src/helpers/worker_jobs.rs:354`). So for a queued build it is *queued since*, and for a finished one `end_time - start_time` is the run itself, not the wait — the same expression `stats.rs:164` averages.
- **Ordering today:** `list_packages` (`aurcache-api/src/package.rs:786-787`) orders `OutOfDate DESC, Id DESC`, so "newest" is hidden behind out-of-date rows; `list_builds_impl` (`aurcache-api/src/build.rs`) orders `COALESCE(start_time, 0) DESC`. The Packages and Builds pages fetch everything and filter/sort client-side through `ViewParams` (`frontend-rs/src/listing.rs:1313`: `status: StatusFilter` with `OutOfDate`/`State(BuildState)`, `sort: Sort`, and for Logs `severity`), so "View all" links need only build the right `ViewParams`. That filter is single-valued today: `StatusFilter` is `Any | OutOfDate | State(BuildState)`, written to the URL as one `s=<slug>` (`listing.rs:1405`) and picked from a plain `<select>` in the shared `ListControls` (`listing.rs:1032`).
- **Out of date is usually handled already, but only via the *global* setting.** `build_on_new_version` makes the version checker enqueue a build itself, and `auto_update_interval` does the same on a schedule; both read the setting through `ApplicationSettings::get(.., None, db)` (`update_version_check.rs`, `auto_update.rs`) — `pkgid: None`, i.e. never a per-package override, and both funnel through `package_update_all_outdated`, which also skips any package whose last build failed. A per-package override of either setting changes nothing about what actually happens, so a dashboard rule that consulted one would disagree with the server.
- **Indexes today:** outside the log tables, only `idx_packages_name` and `idx_builds_pending_pkg_platform`. Nothing covers `builds.start_time`, `builds.status` or even `builds.pkg_id` (the partial index only holds pending rows), so `latest_successful_version_expr` (`aurcache-db/src/helpers/builds.rs:162`, `pkg_id` + `status`), run once per row of every package listing, scans the builds table; `total_artifact_size_expr()` is a correlated subquery over `files`, computed per row.
- **Design system:** `daisyUI 4.12.14` + `Tailwind CDN`, `index.html:11-38` theme variables (`--p`, `--su`, `--bc`), cards `card bg-base-100`, titles `card-title text-base`, muted `opacity-60/70` legends already used in chart header `dashboard.rs:48-61`.

## Constraints And Non-goals
- **No fork of `dioxus-charts`:** theme/layout stay in `index.html` CSS as done for the chart fix; crate patch is not reintroduced.
- **Backend improvements are in scope when they surface more meaningful info or save work:** a purpose-built endpoint is preferred over shipping a card that sorts whole lists client-side or shows the wrong "recent".
- **No heavy dashboard polling:** keep `use_poll(..., false)` slow tick, `limit=5` per section, no auto-refresh of logs every second.
- **Non-goals:** per-package build queue, worker detail, full log search, editable settings on the landing page, hover tooltips on the chart (crate has no hover props), `sort`/`status` parameters on the list endpoints (the list pages filter client-side and would not use them), a CLI command for the new endpoint.

## Key Decisions
- **Layout: 1 + 1 + 2×4, responsive, two viewports at most.** `StatTiles` (full width, 5 cards) → `Builds per month` (full width `h-64`) → `Recent packages | Recent builds` → `Failed | Out of date` → `Stuck queue | Recent problems` → `Largest | Longest builds` (`lg:grid-cols-2` each, `N=5`). Eight cards. Stuck queue sits beside problems because both answer "is the system doing its job right now", and the slow-moving Largest/Longest pair goes last. Single column wastes `lg`; 3-col is cramped for log lines.
- **One dashboard endpoint, not list parameters.** `GET /stats/dashboard` returns every slice in one `DashboardView` (in `aurcache-common/src/api/stats.rs`, beside `ListStats`), computed in `aurcache-api/src/stats.rs` with the slices' queries run concurrently. The alternative — `?sort`/`?status` on `/packages/list` and `/builds` — adds query surface to two public endpoints that only the dashboard would call, and costs eight requests per tick instead of one. Each section is `Option<…>`: `None` when its query failed (logged with `tracing::warn!`, like `annotate_waiting`), so one bad query still never blanks the page. `stats` and `graph` stay separate: they exist, the CLI reads `stats` (`aurcache-cli/src/main.rs`), and folding them in buys one request.
- **Build indexes, in a migration.** `idx_builds_start_time (start_time)` for recent builds, and `idx_builds_status_start_time (status, start_time)` for the queue (`status IN (ENQUEUED, WAITING_FOR_DEPS) ORDER BY start_time ASC`, and its count) and the longest-builds window (`status = SUCCESSFUL_BUILD AND start_time >= since`). `list_builds_impl` today orders by `COALESCE(start_time, 0)`, which no plain index serves; the migration backfills any `NULL` `start_time` (legacy rows — every enqueue sets it now) with `end_time` or `0`, and the query then orders by the bare column. `idx_builds_pkg_status_start_time (pkg_id, status, start_time)` serves the per-package lookups: the previous successful build behind each longest-builds row, and `latest_successful_version_expr`, which every package listing runs once per row. Packages get no index: `packages.id` is the primary key, and a size sort over a few hundred packages is cheap. Backend-agnostic `Index::create`, no raw SQL.
- **Stuck queue means stuck, not queued.** A busy instance always has a queue; listing it says nothing. The card lists `ENQUEUED`/`WAITING_FOR_DEPS` builds oldest first, and marks each with what is holding it: the server's `waiting_reason` when no approved worker can take it (the same one `aurcache doctor` presents), "waiting for dependencies" for `WAITING_FOR_DEPS`, and otherwise just its age. The card title carries the total queue depth.
- **Recent problems, not recent activity.** Five unfiltered log entries are mostly version checks and queued builds, which the other cards already show better. The card reads the log at `Severity::Warning` and worse, and "View all" opens the full Logs page, where the rest is.
- **Out of date means "needs a hand".** The card lists out-of-date packages that nothing will rebuild on its own. Both auto-rebuild paths — the version checker's immediate rebuild and the scheduled auto-update job — go through `package_update_all_outdated`, which reads `build_on_new_version` and `auto_update_interval` **globally only**, never per package, and skips any package whose last build did not succeed. So "needs a hand" is: the package's out-of-date set, restricted to packages whose last build succeeded (a failed one belongs on the Failed card instead — the same restriction the frontend's own out-of-date badge already applies, via `StatusFilter::matches`), then excluding any with an active or queued build and any covered by a global setting. A per-package override of either setting is not consulted by the setting's real effect, so it must not be consulted here either — doing so would show a package as "handled" that nothing will actually rebuild, or vice versa. Two global lookups, run once per request, not per package.
- **Longest builds over a window, with the previous run beside each.** An all-time list barely changes and prompts nothing. The card ranks successful builds that started in the last `LONGEST_WINDOW_DAYS` (30), shows each one's `platform` — an emulated armv7 build is always long, and the tag says why — and its previous successful build's duration on the same platform, so "42m, was 12m" reads as a regression and "42m, was 41m" as normal. `previous_secs` is a correlated scalar subquery in the select, in the style of `latest_successful_version_expr`: the same package and platform, `SUCCESSFUL_BUILD`, `start_time` before this build's, newest first, `LIMIT 1`. That is at most five lookups, each served by the `(pkg_id, status, start_time)` index. No window function: `LAG` is backend-specific enough to need sign-off, and the subquery is the existing idiom.
- **Collapse the attention cards when they are empty.** Failed, Out of date and Stuck queue with nothing to show render as a one-line card (`card-body py-3`, a success-toned check and "No failed packages" / "Nothing needs a hand" / "Nothing queued"), not a full card holding an empty-state alert. Largest, Longest and the recents keep their full card: empty there means "nothing yet", which is worth a sentence and a link. The collapsed card needs `self-start` on its own root: a grid row stretches every cell to its tallest item by default, and a collapsed card's row-mate is often the full-height kind — without it, "collapsed" still occupies the row's whole height, just with empty padding under the one line.
- **The list filter takes several statuses.** The stuck queue spans two states (`Enqueued`, `WaitingForDeps`), and a single-valued filter cannot link to it. Rather than a `Queued` special case, `StatusFilter` becomes a set: `StatusFilter { states: StateSet, out_of_date: bool }`, empty meaning any. `StateSet` is a bitset over the six `BuildState`s (`build_state.rs:19`), so the filter stays `Copy`; `Any` stops being a variant. Out of date stays a flag since it is not a build state, but combines with the states, so the Packages page gets "failed or out of date" — a row matches if it meets any selected condition. In the URL it is comma-joined slugs, `s=enqueued,waiting`; an unknown slug is dropped rather than turning the whole filter to any, and only a value with nothing recognisable falls back to everything. `ListControls` swaps its `<select>` for a dropdown of checkboxes whose button summarises the choice ("Any status", "Failed", "2 statuses"); it is shared, so both lists get it. Parsing sets without the control would be worse than neither: a dashboard link would land on a filter the page cannot show or reproduce.
- **Cap at 5 and link out.** Recent packages are directly requested only, matching the `StatTiles` headline. Each card's "View all →" opens its canonical list with the matching `ViewParams`.

## Recommended Approach
- **`DashboardView`** (`aurcache-common/src/api/stats.rs`):
  ```rust
  pub struct DashboardView {
      pub recent_packages: Option<Vec<SimplePackage>>, // directly requested, Id DESC
      pub recent_builds: Option<Vec<BuildSummary>>,    // start_time DESC
      pub failed: Option<Vec<SimplePackage>>,          // packages.status = FAILED_BUILD (latest build state)
      pub out_of_date: Option<OutOfDateSlice>,         // { needs_hand: Vec<SimplePackage>, handled: u64 }
      pub queue: Option<QueueSlice>,                   // { depth: u64, oldest: Vec<BuildSummary> }
      pub problems: Option<Vec<LogEntry>>,             // severity >= Warning, newest first
      pub largest: Option<Vec<SimplePackage>>,         // total_artifact_size_expr() DESC
      pub longest: Option<Vec<LongBuild>>,             // { build: BuildSummary, previous_secs: Option<i64> }
  }
  ```
  The package rows reuse `list_packages`' select (factored out of `package.rs` so the columns cannot drift), the build rows `build_row_select()` + `annotate_waiting` from `build.rs`, the problems `LogStore::page` (`aurcache-activitylog/src/log_store.rs`) with a `LogFilter` at `Severity::Warning`. `previous_secs` is `None` when there is no earlier successful build on that platform, never `0`.
- **Frontend:** `Dashboard` stays a `space-y-4` stack: `StatTiles`, `BuildsChart`, then one `use_resource(|| client.dashboard())` + `poll::use_poll(resource, false)` feeding four `grid gap-4 lg:grid-cols-2` rows: `RecentPackagesCard | RecentBuildsCard`, `FailedPackagesCard | OutOfDateCard`, `StuckQueueCard | RecentProblemsCard`, `LargestPackagesCard | LongestBuildsCard`. Each card is a `#[component]` taking its section's `Option<…>`, so it is testable with `dioxus_ssr` without a client. While the resource is first loading the eight cards render as skeletons (`skeleton` blocks in the card's full shape: title bar and five row bars), not eight spinners; the chart sits above them and loads on its own request, so nothing above them moves; `Some(Err)` of the whole request is one `alert-error` across the grid; a `None` section is an `alert-error` inside its own card.
- **Card chrome:** `card bg-base-100 shadow-xl`, `card-body`, `card-title text-base`, header row `flex justify-between items-baseline` with title left and `Link { class: "link link-primary text-xs", "View all →" }` right. Links: Recent packages / Largest → `Route::Packages` (default view); Failed → `Route::Packages` filtered to `failed`, **dependencies shown**; Out of date → filtered to out of date (`s=outdated`), **dependencies shown**; Recent builds / Longest → `Route::Builds`; Stuck queue → `Route::Builds` filtered to `enqueued,waiting`; Recent problems → `Route::Logs` with `severity: Some(Warning)`. Dependencies shown on the first two: neither dashboard query filters on `directly_requested`, so a dependency package can appear on either card, and the default Packages view hides dependencies — without this the link a card gives for its own rows would come up short.
- **Recent packages rows:** name via the `PackageBadge` pattern (`screens/packages.rs`), status via `BuildStatusBadge`, row is a `Link` to `Route::Package { pkgbase }`. Empty: "No packages yet. Add one →".
- **Recent builds rows:** `pkg_name`, `#number`, `BuildStatusBadge`, `version`, `AbsoluteDate` (`start_time`), row links to the build.
- **Failed rows:** package name, `latest_version`, links to the package. Collapsed when empty.
- **Out of date rows:** package name, `latest_version → upstream_version`, links to the package; the `handled` count as a muted footer line when non-zero. Collapsed when `needs_hand` is empty, keeping the count ("Nothing needs a hand · 4 rebuilding on their own"). The slice itself is restricted to packages whose last build succeeded, matching what the frontend already calls "out of date" (`StatusFilter::matches`) — a failed rebuild attempt shows on the Failed card instead, not here.
- **Stuck queue rows:** `pkg_name`, `#number`, `platform`, and the holding reason (`WaitingReason`'s `Display`, "waiting for dependencies", or nothing), with the queued age right-aligned (`AbsoluteDate` of `start_time`). Title "Stuck queue · {depth} queued". Row links to the build. Collapsed when `depth == 0`.
- **Recent problems rows:** each row `flex gap-2` with the `Severity` badge (`badge badge-warning`/`badge-error`), `AbsoluteDate`, and the entry rendered as the Logs page renders it (`EntryText` in `screens/logs.rs`): each entity its sentence names is a `Link`, and an entry that does not decode falls back to its stored `message`. Empty: "No warnings or errors".
- **Largest rows:** package name, `format_bytes(total_size)`. The query excludes a `NULL` `total_size` (no files, or an unknown size) rather than sorting it: SQLite puts `NULL` last in `DESC`, Postgres puts it first, so leaving it in would put unbuilt packages ahead of the real largest ones on the backend the TrueNAS deploy actually runs.
- **Longest rows:** `pkg_name`, `#number`, `platform` badge, `format_secs(duration)`, and "was {format_secs(previous_secs)}" muted when known. Title "Longest builds · 30 days".
- **Styling:** muted `opacity-60`, dividers `divide-y divide-base-200`, rows `py-2 flex justify-between`, cards `shadow-xl`, `line-clamp-2` on problem text. Chart stays `chart-box h-64` with existing themed CSS.

## Risks / Rollback
- **Unindexed sorts:** package size (a correlated `files` subquery per row) and build duration are expressions no index serves. They stay cheap at this scale — packages number in the hundreds, and the duration sort only sees the 30-day window the `(status, start_time)` index narrows to. Check the `EXPLAIN` of each slice in review, on SQLite and Postgres.
- **Three new indexes cost writes:** every build insert and status change updates them. Builds are written a handful of times each over minutes, so this is noise, and the `pkg_id` one speeds up every package listing besides.
- **Filter URL change:** existing links carry a single slug, which is a one-element set in the new syntax, so they keep working unchanged.
- **A slow slice holds the whole response:** one request means the slowest query sets the dashboard's latency. Mitigation: `LIMIT 5` everywhere, the indexes above, and the tiles/chart are separate requests, so the top of the page never waits on it. Rollback for any one slice is to return `None` from it; the card then shows its error line and the rest are unaffected.
- **Problem prose length:** long entries could wrap and push layout. Mitigation: `line-clamp-2`, consistent row `min-h`.

## Open Questions
- None blocking. `N=5` and `LONGEST_WINDOW_DAYS=30` are single constants, easy to change after seeing a real instance.
